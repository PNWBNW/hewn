# src/chain/generated — bindings generated from the programs' ABIs

Step 2 of `docs/VEIL.md`: TypeScript generated by `@provablehq/veil-codegen` from each program's
ABI, in place of hand-written record parsers. Three programs so far:

| Program | ABI | Bindings | Used by |
|---|---|---|---|
| `hewn_letters_v2` (and v1, whose three records are the same, field for field) | `hewn_letters_v2.abi.json` | `hewn_letters_v2.ts` | `parseLetterRecord` in `../letters.ts` |
| `employer_agreement_v5` | `employer_agreement_v5.abi.json` | `employer_agreement_v5.ts` | `../agreement_records.ts`, which the worker's reader (`../work/agreements.ts`), the employer's (`finalAgreements`, `sentOfferPlaintext` in `../offer.ts`) and `../parties_key.ts` share |
| `employer_agreement_v4` | `employer_agreement_v4.abi.json` | `employer_agreement_v4.ts` | the same; a record's id says which program it belongs to (two u128 words, or 32 bytes) |

Not yet: `packages/records/src/agreement_reader.ts` (the team import's worker list and the
credential authorisation) still reads agreement records by hand; a package can't import the
app's generated folder, so it moves when the bindings do (a package of their own).

**Never edit a generated file.** Regenerate it: `pnpm --filter @pnw/business codegen` (the config
is `apps/business/codegen/veil.config.json`). `generated.test.ts` fails when a checked-in file
differs from what the generator makes from the checked-in ABI.

**Where an ABI comes from.** Built by Leo 4.0.0 from the program's source in `pnw_mvp_v2`
(`leo build` writes `build/abi.json`), from a copy whose build is the deployed bytecode (byte for byte for letters
and agreement v5; agreement v4's deployed copy carries one more blank line, from its upgrade), so it carries the parameter names (`to`, `lookup`, `parcel`) that an ABI made from
bytecode (`leo abi`) can't. `generated.test.ts` checks its records against the deployed bytecode
in `test/devnode/programs/`, field for field and type for type.

**What the app takes from here: the decoders only** (`toLetter`, `toPage`, `toSentLetter`), with
Veil's `parseRecord` turning Shield's record text into what they read. Each file also carries a
contract factory (`create...Contract`) built on Veil's wallet client; the app never calls it,
`scripts/check_signing_path.py` refuses it outside this folder (every write goes through
Shield, INV-11), and the bundler drops it. `scripts/check_program_names.py` lets these files
name their program (veil-codegen writes the id from the ABI) only when they start with the
generator's header, and `generated.test.ts` pins the id to `@pnw/config`.

**What stays Hewn's own**, on top of the decoders (`../letters.ts`): the counts the app needs (two
lookup halves, 34 or 256 parcel fields) and the ranges (a `u128`, a field below 2^248). The
decoders read numbers without checking their type suffix; a program's records can't hold
anything else, and `../letters_generated.test.ts` writes down that difference and the two places
the generated path is stricter than the hand parser it replaced (`test/legacy/`).
