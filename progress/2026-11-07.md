Joshua's "let's keep building Veil under the hood". The second devnode test file,

live bytecode (`programs/`, sha256 `a81fec03…ed19`, read from the explorer 2026-11-06 and 11-07,
the same bytes), driven by Hewn's own code:

- An offer built by `createOfferInputsV5`: the worker's copy read by `parseAgreementRecords`
  (kind, id, parties key, both addresses, terms hash, the employer's half), the employer's
  `SentOffer` found by `sentOfferPlaintext`.
- The acceptance by `acceptCall`, signed by the worker's own generated, funded account: the
  worker's final copy carries both halves, and `finalAgreements` reads the worker's half from the
  employer's copy.
- A withdrawal with the `SentOffer`, after which accepting reverts.
- Refusals: an acceptance signed by someone else; the same parties key twice; an offer to
  oneself; the same terms at the same second to someone else. The finalize-level ones are pinned
  to Veil's `FinalizeRevertError`, so they fail for the program's reason.

  (`computeAgreementValues`), not the worker, so two identical offers in one second to two people
  collide and the second reverts with its fee spent. The app sends one offer at a time, each
  approved in Shield, so it can't happen there; noted, not changed.
- `harness.ts` now holds what both files share (start, deploy with the checksum, send, open, a
  funded account); the letters test uses it. The devnode README and `docs/VEIL.md` updated: step

## 2026-11-07 — Veil step 2, letters: generated bindings in place of the hand parser

Joshua's "start step 2". The letter records are read through code generated from the program's
own ABI (`docs/VEIL.md` step 2), with the hand parser kept beside it for the comparison:

- **The ABI:** built by Leo 4.0.0 from `hewn_letters_v2`'s source (`leo build`), whose bytecode is
  byte for byte the deployed program, so the ABI carries the parameter names (`to`, `lookup`,
  `parcel`) a bytecode-made one lacks. Checked in at `apps/business/src/chain/generated/`.
- **The bindings:** `@provablehq/veil-codegen` 0.15.0 (2026-10-29, a dev dependency;
  `pnpm --filter @pnw/business codegen`), checked in, never edited. `generated.test.ts`: the file
  equals what the generator makes from the ABI; the ABI's records equal the deployed bytecode's,
  field for field; the program id equals `@pnw/config`'s.
- **`parseLetterRecord`** now runs Veil's `parseRecord` and the generated `toLetter`, `toPage`,
  `toSentLetter`, with Hewn's counts and ranges on top. `veil-core` 0.15.0 moved from a dev to a
  runtime dependency: 8.9 KB (3.7 KB gzipped) in the chain pages' chunk; the contract factory
  the bindings carry is never called and is dropped from the bundle.
- **Side by side** (`letters_generated.test.ts`, and every real record in the letters devnode
  test): the two parsers agree on every letter, page and sent copy, and both refuse the same
  malformed records. Three differences, written down as tests: the generated path refuses text
  without a `_nonce` and a lookup half beyond a `u128` (the hand parser read both), and reads a
  number written with the wrong type suffix (a program's records can't carry one). Two unit-test
  fixtures built letters without a `_nonce`; every real record has one (Hewn passes Shield's
  record text straight into `accept_offer` and `withdraw_offer`, which worked on testnet), so the
  fixtures were fixed, not the parser.
- **Checks:** `check_signing_path.py` rule 8 refuses a Veil writing or contract action, or a
