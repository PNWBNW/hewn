**pnw_mvp_v2 #233, the USDCx stand-in rewritten** (new Leo, flagged first; Fable 5.1). The deployed
`test_usdcx_stablecoin.aleo` can't be copied to a devnode: its constructor lets only the issuer's
account deploy it and only a minter may mint. The stub in `src/stubs` had a different shape from
the deployed program (its own mapping names, no `split`, no compliance record), so a payroll
rehearsal against it would have rehearsed nothing. Read from the deployed bytecode (2026-11-07),
the stand-in now has the same transitions, inputs and outputs in the same order:
`transfer_private(recipient, amount, token, proofs)` returns the compliance record, the sender's
change, then the recipient's Token; `transfer_public_to_private`, `mint_private`, `split`, `join`,
`transfer_public`, `transfer_public_as_signer`; the `balances` mapping; the compliance officer's
address as a constant. `mint_test` credits a public balance out of nothing, and the freeze-list
proofs are taken and not checked (the freeze-list program isn't on a devnode): both on purpose,
written in the file's header. Its tests: 11, four of them refusals (paying or splitting more than
a Token holds, going private or paying publicly with no balance); each test awaits every finalize,
so a public check that fails fails the test. Two things the Leo test runner can't do are written
down: it lets a signer spend a record they don't own, and its signer is a fixed address, which
had made an earlier version's owner checks trivial (the recipients are now other addresses, with
an `assert_neq` against the signer). The registrar's tests read `balances` instead of `account`
(24 pass); the job board's still pass (31). CI gets a step for the stand-in's tests.
`payroll_core_v2`'s README notes that its `execute_payroll` names the stablecoin's outputs the
wrong way round (worker, remaining) against what the deployed program returns (change, then the
recipient's Token); it is deployed and unused, so noted, not fixed.

**Hewn, the rehearsal** (`apps/business/test/devnode/payroll.devnode.test.ts`, in CI after the
letters and agreements): Hewn's own code at every step, nothing mocked.

- `postPayRun` (`@pnw/payroll`) posts Day Construction's run for Ana, Ben and Cy (the parity
  test's figures) in rail mode; `runPayQueue` (`@pnw/rail`) plans the transfers, builds the
  freeze-list exclusion proof against a node that has no freeze list (the read 404s, so the proof
  is two empty leaves, as the rail does), and sends `split` and `transfer_private` exactly as it
  does through Shield, over a `RailWallet` that signs with the node's account and lists its Token
  records as Shield would; `markPaycheckSettlement` writes each settlement back as the Pay panel
  does.
- Checked against the VM: three balanced entries, each linked to the transaction that paid it
  (`source.ref` the run, `source.doc` the paystub hash, the settlement's reference the on-chain
  id, three distinct ids); each worker's view key opens exactly their net pay in that transaction
  and nobody else's; the business keeps funds minus pay; `verifyChain` passes.
- Refusals: a run the business can't cover stops before a call is built ("Not enough balance on
  the rail for this run"); going private with one unit more than the public balance is rejected
  by the node's finalize (`FinalizeRevertError`); a Token the business doesn't own, a worker's,
  can't be spent by it, which the Leo runner lets through and the VM doesn't.
- Not testable this way: paying more than a Token holds. The subtraction underflows inside the
  VM's WebAssembly during local execution and the promise never settles (`Integer subtraction
  failed`, `RuntimeError: unreachable`); the stand-in's Leo test covers it, and the pay queue never
  builds such a call. Written in the test, the README and `memory/lessons.md`.
- `harness.ts` gains `sendTx` (the id with the outputs) and `outputsOf`. The stand-in's bytecode,
  built by Leo 4.0.0 from #233, joins `programs/` with its sha256 and how to rebuild it. The CI
  step, `apps/business/README.md`, `docs/VEIL.md` step 1 and the Now block say what the suite
  covers now; the Phase 2 criterion carries the rehearsal and stays open until the testnet run.
