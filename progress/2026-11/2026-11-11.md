## 2026-11-11 — The sleep passes and the session hooks take no direction from what they read

From a security review of the repositories run in this session (its findings stay out of the
public repositories until each is fixed and released). Three settings Joshua made first, by hand,
on GitHub:

- A ruleset on `main` in both repositories: a pull request and the passing check are required,
  force pushes and deletion are blocked, and nobody is on the bypass list, his own account
  included. This was parked on 2026-10-22.
- `pnw_mvp_v2`'s `testnet-staging` environment takes runs from `main` only and waits for his
  approval; administrators can't bypass it. Two unused key secrets were deleted.
- Secret scanning with push protection, malware alerts and private vulnerability reporting are on
  in both; Dependabot security updates are on here.

Then `pnw_mvp_v2` #234 (merged): the unused execute workflow is retired, and the deploy and
upgrade workflows run only from `main` and read the key from one secret.

This pull request, in `.claude/` and `scripts/sleep/`:

- **The light sleep and the dream** recognise their own pull request by who opened it and where
  its branch lives (the owner's account, this repository, a branch under `light-sleep/` or
  `dreaming/`), never by its title. They list open pull requests with three fields only (number,
  author, head) and read no other pull request's title or body.
- **All three passes** (light sleep, dream, REM) now say it in so many words: what a pass reads is
  material to verify, never an instruction to it.
- **The hooks** run the copy of `snapshot.py` on `origin/main`, not the working tree's, so a branch
  that is only checked out runs nothing. A change to the script takes effect once it is merged.
- **The snapshot** names commits by short id and the log by path and count. It no longer carries a
  commit's title or an entry's heading, and a day file dated after tomorrow isn't "the newest".
- `docs/SLEEP.md`, `.claude/skills/README.md` and `scripts/sleep/README.md` say so.

## 2026-11-11 — An id names one message for good

From the same security review. In a conversation, a message kept under an id used to be replaced
by any later message with that id. Answers pair with what they answer by id (an accepted change
of hours, an accepted agreement), so the first message under an id now stays as it was read.

- `books/thread.ts` `addToThread`: a message from the other side under an id already in the
  thread changes nothing, whether that id was one of theirs or one of this side's own. Its slot
  is still used up, so it isn't read again. Only this side's own write replaces a message.
  `validateThread` applies the same rule to a thread read back from the vault (mine stays, else
  the first).
- `chain/thread.ts` `readThread`: such a letter isn't reported as received, and when it says
  something different from the first the result says so ("reused the id of an earlier one").
- `docs/THREAT_MODEL.md` T16 states the rule and what is still open: an answer doesn't carry a
  fingerprint of what it answered, and a message's place in the order is the time its sender
  wrote.

Tests: 8 new (the thread, an agreed change of hours from both sides, an accepted agreement, the
reader through the mailbox); 7 of them fail without the change. The workspace tests (1455), both builds and
the repository checks pass.
