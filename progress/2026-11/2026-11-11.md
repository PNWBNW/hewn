## 2026-11-11 — An id names one message for good

From the same security review. In a conversation, a message kept under an id used to be replaced
by any later message with that id. Answers pair with what they answer by id (an accepted change
of hours, an accepted agreement), so the first message under an id now stays as it was read.

- `books/thread.ts` `addToThread`: a message from the other side under an id already in the
  thread changes nothing, whether that id was one of theirs or one of this side's own. Its slot
  is still used up, so it isn't read again. Only this side's own write replaces a message.
  `validateThread` applies the same rule to a thread read back from the vault (mine stays, else
  the first).
- `chain/thread.ts` `readThread`: such a letter isn't reported as received, and when it says
  something different from the first the result says so ("reused the id of an earlier one").
- `docs/THREAT_MODEL.md` T16 states the rule and what is still open: an answer doesn't carry a
  fingerprint of what it answered, and a message's place in the order is the time its sender
  wrote.

## 2026-11-11 — "Stay logged in" is a choice, and the documents say what it is

The documents said that key couldn't be copied off the device; a non-extractable key stops a
page's script from exporting it, but the browser still writes its bytes to disk (checked in
Chromium), so anyone with the device or a copy of its browser profile can open the books while it
is kept. It was also ticked by default, and setup and both restores switched it on unasked.
Joshua chose: off by default, asked everywhere.

- `books/StayChoice.tsx` (new): the one tick box, with what it does in plain words. On Log in,

- `@pnw/vault`: a remembered session carries when it was last used, which only moves forward

## 2026-11-11 — A conversation is ordered by this device's clock, not the sender's

From the same security review. A thread was sorted by the time each sender wrote on a message. A
past time was taken as written, so a message could be placed ahead of what the other side had
already read and answered.

- `books/thread_order.ts` (new): `placedAt` and `inOrder`. A message of mine is placed when I
  sent it, one of theirs when it arrived on this device; what arrived together keeps its slots'
  order. `books/thread.ts`, `books/hours_change.ts` and `books/schedule.ts` use it in place of
  their own sorts by send time. The written time is still shown.
- `chain/conversation_backup.ts` `restoreHistory`: on a restored device nothing arrived, so their
  place is rebuilt from the written times kept in slot order (never before the slot before, never
  after now). The existing restore test still brings a conversation back in the order it was had.
- `docs/THREAT_MODEL.md` T16: the rule, what a restore can and can't do, and what is still open.

No message format changed. The earlier plan was to put a fingerprint of what was answered into

## 2026-11-11 — The admin key's reach is written down, and the app won't sign against a changed program

From the same security review. Nine of the programs the app relies on can be upgraded in place by
one key, and an upgrade may change what a function does without changing its name or inputs. A
wallet proves against the newest edition without saying so, and nothing checked.

In `pnw_mvp_v2` first (#235, merged): the manifest records every program's edition and the hash of
its text on chain, `scripts/check_chain.py` compares them with the chain on every pull request

Here:

- `@pnw/config` `EDITIONS`: the edition of each upgradable program this version of the app was

  every `@admin` program the app names (it reads the submodule, now at the merged manifest).
