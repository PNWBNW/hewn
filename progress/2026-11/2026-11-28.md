## 2026-11-28 — A three-layer pair key: P-256, ML-KEM-1024 and an optional shared secret, not wired yet

Joshua's go in session (2026-11-28): a conversation's pair key moves from P-256 alone to three
layers (`docs/NATIVE_HARDENING.md` section 7, on its branch). This is the first of a series: the
cryptographic core and its tests only, in a new package, `packages/pair-keys` (`@pnw/pair-keys`,
layer 2: it takes only the word list from `vault`). Nothing in the app calls it; every pair stays
version 1, made as before.

- **The format, version 2** (`src/format.ts`): a version byte, then parts tagged by algorithm,
  each once, ascending: `0x01` P-256 (the point), `0x02` ML-KEM-1024 (the encapsulation key, or
  the ciphertext), `0x03` HQC reserved and refused until its standard is final; an unknown id is
  refused by number. A version 1 half (the bare point, `0x04`) is told apart by its first byte. A
  half is 1,641 bytes, the answer 3,214: both fit one page, not a letter.
- **Who encapsulates:** the responder, to the initiator's ML-KEM key, which it holds when it
  answers; the ciphertext rides back with the answer, so the handshake stays two messages.
- **The combiner:** HKDF-SHA256, salt the agreement's parties key (as version 1); every secret in
  the extract step, the whole transcript (both halves in their roles, the ciphertexts, the
  version, whether the third layer is used) in the info. Chosen over X-Wing's SHA3-256 combiner,
  whose proof is for X25519 with ML-KEM-768 and leaves the ciphertext out for that pairing.
- **The out-of-band secret** (`src/out_of_band.ts`): 32 to 64 bytes, shorter refused (the plan
  says 128 bits; this work set 256); made as 32 random bytes; written as 26 BIP-39 words (the
  vault's pinned list, now exported as `@pnw/vault/passphrase-words`) or a `PNW-OOB1:` code of 58
  base32 characters for a QR code. An 8-bit hash and two Reed–Solomon symbols over GF(2¹¹): one
  or two wrong words, two swapped, or one wrong character of the code is always caught.
- **The dependency:** `@noble/post-quantum` 0.7.1, published 2026-08-27 (93 days old, the newest
  release), MIT, its three dependencies already locked at 2.4.0. Its README says it is
  self-audited (0.6.1), not independently audited, and not constant-time; it is checked here
  against NIST's ACVP vectors for ML-KEM-1024 (ACVP-Server `975de31e`).
- **Fixtures for the Rust port:** `fixtures/pair_keys_v2.json` (fixed test inputs, each layer's
  secret, the combiner's input, the info's hash, the key; and version 1's), checked both by the
  package and by the construction written out by hand. `apps/business/src/chain/key_ring.test.ts`
  now pins the app's own version 1 `pairKeyHex` to that file's version 1 answer.
- Docs: the package's README (the layers, the format, the HQC slot, the combiner and why), its row
  in `packages/README.md`, the map's Vault region, the decision in the ledger, the Now block.

## 2026-11-28 — The pair-key format reserves a slot for an ML-DSA-65 signature

Joshua's decision the same day: id `0x04` is held for ML-DSA-65 (FIPS 204), a signature by the half's
owner over it, refused by name today like HQC's `0x03`. A signature can't be harvested and forged
later, so it is needed only before quantum computers arrive; until then a half's origin rests on the
Aleo transaction that carries it and, where used, the out-of-band secret. `packages/pair-keys`: the
reserved ids in one table, the README's id table and a paragraph, a test that the slot is refused by
name and one that the id stays 4. pair-keys 46 passed, 1 skipped.

## 2026-11-28 — The answer carries only what it uses, and each pending pair key opens one answer

Joshua's go in session (2026-11-28), stacked on #399 (the pair-key core): two changes to the
version 2 handshake while nothing in the app uses it, so the format changes freely.

- **The trimmed answer** (`packages/pair-keys/src/format.ts`): a message now says what it is
  (`0x02 | kind | count | parts`, kind `0x01` the initiator's half, `0x02` the responder's
  answer). The half carries the P-256 point and the ML-KEM-1024 encapsulation key; the answer the
  responder's P-256 point and one ciphertext per KEM, nothing else: the responder never
  decapsulates, so it sends no KEM key and keeps none, and its P-256 key is made for that one
  answer, non-extractable. An answer that carries an encapsulation key (a half where the answer
  belongs; the two are the same length, the kind byte tells them apart) is refused, and so is a
  half carrying ciphertexts. The combiner's info now binds the two messages whole, the half first:
  `"PNW::PAIR::v2" | 0x02 | flags | len | half | len | answer`.
- **One answer per pending key** (`src/pair_key.ts`): the initiator's `PendingPairV2` (`create`,
  `restore` from the vault's copy, `half`, `toStored`, `complete`, `discard`, `state`). The first
  `complete` spends it before anything else, whatever its outcome (a refused answer included), and
  zeroes the P-256 scalar, the ML-KEM seed and everything made from them; a second answer, the same
  one again or one arriving while the first is opened is refused. Why, in the README: attacks that
  recover an ML-KEM key (decapsulation failures, plaintext-checking oracles) need many ciphertexts
  per key; ePrint 2026/1682 is cited as Joshua gave it (not fetched: the session can't reach
  eprint.iacr.org). The vault's copy could be restored twice, so the key ring (the next PR) must
  remove it in the write that keeps the pair's key; each side keeps the pair's key, not its halves.
- **Ids:** `0x05` reserved for HQC as published in FIPS 207, refused by name like `0x03` (today's
  HQC, its own package) and `0x04` (ML-DSA-65). No HQC here.
- **Sizes** (`src/sizes.test.ts`, measured, against `PAGE_BYTES` and `LETTER_BYTES` read from
  `apps/business/src/chain/letters.ts`): the half 1,642 bytes and the answer 1,642 (was 3,214),
  2,192 base64 characters each: past a letter (1,052), one page each (7,934).
- **The fixture** (`fixtures/pair_keys_v2.json`): rewritten keeping every input (v1, the
  out-of-band secret, both P-256 keys, the seed, the salt, the encapsulation's randomness); each
  layer's secret and the ikm are unchanged, the half, the answer (new), the info's hash and the
  pair keys change; the responder carries only its P-256 key. The writer now keeps the inputs it
  finds. Docs: the package README (format, id table `0x01`–`0x05`, who sends what, one answer per
  key, sizes, the combiner), its row in `packages/README.md`, the decision in the ledger.
