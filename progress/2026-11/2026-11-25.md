## 2026-11-25 — The native verifier: a release and a closed period, checked in Rust on GPUI and snarkVM

Joshua's go (2026-11-25) for the hardened native client's first piece (`docs/HOSTING.md`, "Later: a
hardened native client"). `apps/native`, its own Cargo workspace:

- **`pnw-verify`, the library and a command-line tool.** A release folder checked as
  `scripts/release/verify.mjs` checks it (the canonical list and its digest, the Ed25519
  signature against `releaseKeys` or `--key`, every file and nothing else, the commit as the build
  id, the anchor on request), and a period proof as `/verify` checks it (every entry's BLAKE3 hash
  over `JSON.stringify` of its canonical array, range, order, the leaves, both Merkle roots and the
  period root; then the anchor in `audit_event_height`, the block after the range, every payment's
  transaction). The same labels and reasons. Stricter in three places, all written down: string
  fields must be strings, Ed25519 is verified strictly, transaction ids must pass snarkVM's
  checksum.
- **snarkVM** (`snarkvm-console` =4.13.1, published 2026-11-17; testnet ran 4.12.0 per
  `pnw_mvp_v2`'s toolchain): the period root has no Aleo hash in it (BLAKE3 and HMAC), so what
  snarkVM does natively is the anchoring transaction: the public future's output id (Poseidon8,
  the function id by BHP1024), each transition's id (BHP512 over its BHP Merkle tree) and the
  transaction's id recomputed from the explorer's JSON. October's
  (`at1hg2etspa…p500eq`, root `95496641…e68b`, block 21,235,519, made 2026-11-07) recomputes
  exactly, offline from a trimmed copy and live.

  choice of the day, over Zed's repository directly): a release folder, a proof file, or a

  product's name and colours, the credit and the source link from `@pnw/brand`. Opened on a virtual
  display here and run against the live explorer on October's data: every check passed.
- **Generated, never hand-written:** `verify/src/generated.rs` from `@pnw/brand` and `@pnw/config`
