## 2026-10-22: team events (invitations and answers)

event can have guests: a business invites people on its team; a person invites their employer and

- **How it travels** (`docs/LETTERS.md`, "Shared events"): each organizer keeps a random key for

## 2026-10-22: never pay twice (fix 2 of the security review)

Before, a paycheck whose payment had gone out could be marked failed and paid again by Retry: an
explorer error in the three minutes after Shield accepted (a 429, a 503, a timeout), Shield not
answering within 15 minutes, Shield accepting without an id, the page closing between the
approval and the vault write, or two tabs paying one run.
- **The record is the guard** (`packages/rail/src/queue.ts`): before Shield is asked for a
  transfer, the pay screen keeps a tag for the record it will spend (`Settlement.attempt`, the first
  16 bytes of SHA-256 over the record; awaited: if it can't be kept, nothing is sent). A later run
  sends that paycheck again only by spending the very same record, so if the first transfer is
  still on its way the network lets only one through. If the record is gone, the payment may have
  gone out: it's shown as not confirmed, never sent on its own.
- **Unknown isn't failed:** no answer in time, or accepted without an id, is "not confirmed"
  (kept pending with what's known); a later run asks Shield about it again for two minutes. Only a
  definite answer (declined, rejected by Shield or by the explorer) is "failed". An explorer that
  can't be reached only delays confirming; after three minutes it settles on Shield's word, as
  before.
- **Paying again is a choice:** a not-confirmed row says to check Shield's activity, with "Pay
  again anyway" ("only if Shield's activity shows no payment to them for this amount").
- **Two tabs** (`books/vault_write.ts`): every vault write checks, under a lock across the
  browser's tabs, that the stored books are still what this tab last saw, and refuses ("changed in
  another tab or window… reload") instead of overwriting. That also stops two tabs undoing each
  other's work anywhere in the app.
- `docs/THREAT_MODEL.md` T5 has the paragraph.

Tests: rail 44 (+5: an explorer down after acceptance settles; accepted without an id is
unconfirmed; every tag kept before Shield is asked, and a payee whose tag can't be kept isn't
sent; a retry spends the same record and one whose record is gone isn't sent; a lost one is asked
about again, briefly); payroll +1 (the attempt note); app +2 (two tabs). Every package passes

## 2026-10-22: who a letter is from (fix 3 of the security review)

Apart from event invitations, a letter was believed because it opened with the right key. So any
member of a channel could seal a fake team schedule or announcement into the business's next slot
and send it to coworkers (and hide the next real post); anyone could apply "as" someone else's
name; an auditor shown a view key could write into a hired pair's conversation; and a group member
could make themselves a group's admin on another member's screen.
- **The reader checks the sender** (`chain/letters.ts` `letterReader(letters, from)`): a slot's
  letter counts only when the record's sender (visible only to its owner) is the account expected.
  `letterThread`'s reader is bound to the other side, which covers every conversation; channel
  posts are read against the business (worker's Messages check); coworker letters against the
  account the business listed (none listed: not read); hours, paystubs and offer terms against the
  person or the employer (`scanHours`/`scanPaystubs` take a reader per account). When Shield shows
  no sender at all, the check stops and says so instead of guessing.
- **Applications** (`chain/applicants.ts` `applicationFrom`): kept only when the sender owns the
  registered name claimed; others are counted ("not sent by the name's owner, left out").
- **Group chats** (`books/groups.ts`): the admin is whoever set the group up first as this device
  saw it, on this device's own times; two members' messages with one id stay two messages.
- **Send times** (`chain/thread.ts`): a received message dated in the future takes the time it
  arrived.
- Docs: `docs/LETTERS.md` ("No from"), `docs/THREAT_MODEL.md` (channels, and a new section).

Tests: a forged team-schedule post sent by a member is ignored and the real post in the same
slot still read (fails on the old reader); the reader picks the expected sender, ignores another,

## 2026-10-22: names shown only when they check out (fix 4 of the security review)

`pnw_name_registrar_v5` stores whatever text it's given beside a name's hash (`NAME_REGISTRY_MAP.md`
#2), and the app showed that text as the name: anyone could register their own hash with the text
"acme" for free and show as acme.hewn on the job board, as the sender of an offer, in the review
list's counterparty, or in an account lookup.
- **`nameMatchesHash`** (`@pnw/records`): a name counts only when it hashes back to the hash it's
  filed under and is a plain name (`a-z`, `0-9`, `_`, 3 to 16; no look-alike characters).
  `queryNamePlaintext` returns null otherwise, so the board ("A business"), offers (the account),
  lookups and the review list all fall back to the account.
- **Kept before the check:** an employer name saved on an agreement is reused only if it still
  checks out; an applicant's name shows only if it checks out (else "account (name not
  verified)"), and a new application whose name doesn't match its hash is left out.
- **Sold-back names:** an account's primary name counts only while the account still owns it
  (`lookupAddress`), so a name it sold back, maybe someone else's now, isn't shown for it.
- Docs: `docs/NAME_REGISTRY_MAP.md` #2, `docs/THREAT_MODEL.md` ("Who a letter is from").

Tests: records +2 (the check, and the registrar read refusing "acme" against another hash, a
Cyrillic look-alike, upper case); app +1 (an account showing a name it no longer owns; the
application test now also covers one posing as another name). Every package passes (1042); both
builds pass; `pnpm audit` clean.
